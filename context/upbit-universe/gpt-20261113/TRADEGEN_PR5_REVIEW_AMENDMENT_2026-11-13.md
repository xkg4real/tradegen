### 2. 저장 영역과 식별자

#### 2.1 영역 분리

1. `workspace/`: 초안, 편집용 설정, 표시용 미서명 보고서. 사용자 작업 폴더에 둘 수 있다.
2. `staging/`: 확정 저장소와 같은 로컬 파일시스템의 전용 임시 영역. 수집·평가 writer만 쓴다. 종료 표시만으로 확정하지 않는다.
3. `sealed/`: OneDrive 및 알려진 동기화 루트 밖의 전용 로컬 저장소. 사용자 문서 편집과 동기화 충돌로 직접 변경되지 않도록 운영 계정 ACL과 서비스 권한을 분리한다. 링크·junction·reparse·경로 우회도 검사한다. 읽기 전용 속성만으로 불변성이 증명된다고 간주하지 않는다.
4. `backup/`: 별도 위치의 버전 보존 저장소. 가능하면 다른 장애 영역에 둔다. 이전 버전을 지우거나 최신 파일로 덮어쓰지 않는다. 보호된 저장소가 마련되기 전에는 백업 완료/복구 가능 상태를 표시하지 않는다.
5. `quarantine/`와 `incidents/`: 손상본·중단 묶음·사건 원인·검사·복구 결과 보존. 기존 서명 대상 파일은 사건 기록을 덧붙이기 위해 수정하지 않는다.

구체적인 로컬 경로, 백업 매체, 암호화/보존 정책은 배포 설정이다. 개인 경로나 계좌 수치는 공개 저장소에 넣지 않는다. 알려진 동기화 루트 점검은 가능하지만 모든 외부 동기화 도구를 탐지한다는 보장은 하지 않는다.

#### 2.2 재계산과 재수집 식별

- 매 시도에 새로운 `research_run_id`, 증가하는 `revision`, `attempt_id`, `parent_bundle_sha256`를 부여한다. 원본 bundle은 덮어쓰지 않는다.
- 원본 capture 안의 사전등록 `protocol.study_id`, 등록 시각, 관측 시각은 역사적 사실이므로 이름 변경을 위해 수정하지 않는다. 재계산 bundle의 새 식별자와 원본 capture의 식별자를 분리해 계보를 명시한다.
- 온전한 과거 자료를 새 계산기로 평가한 결과는 새로운 평가 버전이며, 새 사전등록 관측처럼 표시하지 않는다. 기존 연구 승인도 자동 승계하지 않는다.
- 새 관측을 수집하는 연구는 새 프로토콜/후보군/시도를 관측 전에 등록한다. 기존 시도와 탈락·실패 내역을 가족(family) 및 prior-attempt 기록에 유지해 다중 시도 계산에서 제거하지 않는다.

### 3. 확정 bundle 프로토콜

#### 3.1 manifest와 승인 연결

신규 `tradegen-research-bundle/1` manifest에 최소 다음을 포함한다.

- `research_run_id`, `revision`, `attempt_id`, 부모 bundle, 프로토콜·등록·전체 후보 목록/순서, 관측 구간, 계산기 및 수집기 revision.
- `files[]`: 정렬된 상대 경로, 역할, 정확한 바이트 길이, SHA-256, 필수/선택 구분. 경로 중복, 대소문자 충돌, Windows 예약명, ADS, 절대경로, `..`, 링크는 거절한다.
- 원본 프로토콜/등록/공개 commitment 증거, 모든 후보 capture, 조회 성공·정상 실패를 포함한 원시 receipt, snapshot/규칙, 결정·결과, 계산기 코드/의존성 식별, 서명 대상 보고서의 전체 파일 목록.
- `complete` 및 completion/실패 사유. 저장·수집 중단으로 `complete=false`인 묶음은 확정 `sealed`에 게시하지 않고 별도 중단 시도 보관 영역과 사건 목록에 보존한다. 모든 필수 기록이 온전하지만 후보가 정당하게 평가 실패한 경우와 구분한다.
- 후보별 상태: `EVALUATED`, `EVALUATION_FAILED` 또는 수집 중단 기록. 숫자 수치는 실제 `ValidationResult`에만 존재한다.

manifest의 canonical bytes 해시를 **새 승인 증거에 명시적으로** 포함한다. 기존 schema-2 family hash도 함께 유지한다. 기존 `audit_sha256`에 manifest를 넣었다는 이유만으로 전체 경로가 검증된 것으로 처리하지 않는다. 현재 verifier는 그 파일목록 의미를 검증하지 않으므로 새 manifest parser·검증기·서명 대상 정의가 필요하다.

순환 참조를 피한다. evidence manifest는 서명 파일 자체를 포함하지 않는다. 이후 생성되는 detached approval은 manifest 해시 및 승인 범위를 서명하고 별도 버전 저장한다. 백업 인덱스가 evidence와 detached approval을 함께 연결한다. 보고서를 새로 꾸민 경우, 미서명 표시본은 원본 bundle 해시를 표시하고 승인 증거처럼 보이게 하지 않는다. 서명 대상 보고서 수정은 새 bundle/revision/승인이다.

#### 3.2 게시 순서

1. 전용 staging의 새 묶음에만 기록한다. 동일 ID 재사용은 거절한다.
2. 모든 writer를 닫고 파일별 flush/fsync를 완료한다. manifest도 마지막에 작성하고 flush한다.
3. manifest의 파일집합과 실제 필수 증거 집합을 대조한다. 빠진 후보, 여분의 충돌 파일, 잘린 기록, 잘못된 형식, 전체 해시, 시간·결정·계보를 검증한다. writer를 배타적으로 종료하고 읽기 핸들에서 파일 식별·길이·내용을 검증한다. 경로를 검사한 뒤 나중에 다시 여는 것만으로 TOCTOU 변경 방지가 충족됐다고 간주하지 않는다.
4. 같은 볼륨에서 새 목적지로 원자적 no-replace 게시하되, 아직 catalog에 공개하지 않은 `PENDING_VERIFY` 버전으로 둔다. 게시된 버전은 운영 writer가 수정할 수 없도록 전용 소유권·ACL을 적용한다. Windows 디렉터리 rename/파일 flush와 POSIX 디렉터리 fsync의 차이를 구현·장애 테스트한다. `READY` 파일 하나만 존재한다고 신뢰하지 않는다.
5. 게시된 목적지의 전체 파일과 manifest를 검증용 핸들로 다시 읽어 식별·내용·완전성을 확인한 뒤에만 catalog 트랜잭션으로 `VERIFIED_UNAPPROVED` 상태에 승격한다. 승인 대상과 소비할 bytes를 같은 고정 버전에 바인딩한다. 실패한 staging/orphan과 `PENDING_VERIFY`는 조사용으로 보존하지만 일반 reader·선발기·활성화 경로에서는 발견하거나 읽을 수 없게 한다.
6. 별도 위치에 버전을 복사하고 전체 read-back 검증 및 backup receipt를 남긴다. 승인 받은 detached evidence도 별도로 보존·대조한다. 백업이 실패하면 재시도하고 상태를 알리며, 백업 완료인 척하지 않는다. catalog 등록은 승인과 다르며, 검증된 백업·필요한 서명·현재 조건 검증이 모두 충족되기 전에는 승인된 연구 상태로 승격하지 않는다.

모든 일반 reader는 catalog에 검증 완료로 등록된 고정 버전만 읽으며, 미승인 버전은 검토 목적에만 사용한다. 선발·활성화 reader는 승인 상태와 manifest/서명/현재 조건을 사용 직전에 다시 검증한다. 읽기 핸들·내용 해시·게시 버전 식별을 묶고, 경로 변경이나 게시 후 변형이 확인되면 보류한다. 앱이 관리하는 ACL과 불변성은 관리자나 디스크 손상을 막는 절대 보장이 아니므로 주기적 scrub과 사용 직전 검증을 함께 사용한다. 해시 일치는 기록의 동일성이지 시장 데이터 출처가 참이라는 인증은 아니다. 기존 출처 검토를 대체하지 않는다.

### 4. 후보 결과와 손상 분류

#### 4.1 정상 조회 실패

예정된 조회에 대해 시간·대상·수집기 revision·고정 실패 코드·가능한 원시 receipt·응답 유무가 형식에 맞게 남아 있으면 정상적으로 기록된 unavailable 관측이다. timeout과 실패 응답을 섞거나 실패를 정상 빈 결과로 바꾸지 않는다. 불완전/실패 관측은 사전 지정한 평가 규칙에 따라 탈락 또는 전체 연구 불충분이 될 수 있으며, 평가 불가능한 수익률을 생성하지 않는다.

#### 4.2 손상 또는 입증 불가

필수 slot/후보/파일 누락, 중간 잘림, malformed JSON, 중복 키, 원본 해시 불일치, 잘못된 등록/결정 prefix, 시각 역행, 선언하지 않은 파일 대체는 정상 unavailable 사유가 아니다. 해당 완전 후보군의 승인·선발을 보류한다. 초반의 정당한 탈락을 발견해도 뒤쪽 프레임 검사를 생략하지 않는다.

#### 4.3 공용 평가 결과

- 공용 함수는 모든 후보의 원본 전체를 먼저 검증한 뒤 `ValidatedCandidateOutcome`을 발급한다.
- 성공 계산은 기존 `ValidationResult`와 실제 지표를 유지한다. 수학적 탈락도 이 분류 안에서 결과를 그대로 보존한다.
- allowlist에 있는 정당한 universe 평가 실패만 별도 `tradegen-candidate-evaluation-failure/1`로 발급한다. 고정 사유, 발생 slot/단계, 원본 전체 해시, protocol/registry/전체 inputs 해시, evaluator revision을 바인딩한다. 정상 결과 해시와 다른 도메인을 사용한다.
- 광범위한 예외 catch로 실패 outcome을 만들지 않는다. 새 코드의 버그·누락·손상은 가족 전체 보류 사유다.
- `study._select`와 `authenticate_study_selection`은 동일 함수를 사용한다. schema-2 family는 성공/탈락/허용된 실패 모두를 포함한다. 순위는 실제 계산 결과 중 적격 후보에만 부여한다. 전체 후보군/이전 시도 수를 줄여 다중검정 보정을 유리하게 하지 않는다.
- 벤치마크가 평가 불가하면 선발 없음. 모든 후보가 탈락하면 선발 없음. 후보 삭제 후 나머지로 다시 같은 연구를 승인하지 않는다.

### 5. 손상 사건의 4단계 처리

네 단계는 판단 순서이며 성공한 복구가 뒤 단계를 강제하지 않는다. 사건 상태는 외부 append-only 기록에 남긴다.

| 단계 | 시작 조건과 동작 | 승인·거래에 미치는 영향 |
|---|---|---|
| ① 정확한 원본 자동 복구 | 손상본 격리 → 신뢰 anchor에서 승인 증거 검증 → 서명에 연결된 manifest와 모든 파일이 정확히 일치하는 버전 백업 탐색 → 새 staging에 전체 복원 → §3.2의 비공개 게시·목적지 전체 재검증 → 검증된 참조로 전환 | 원래 bytes·해시·등록·승인 범위가 같고 서명 만료/폐기/현재 코드·규칙 등 모든 조건이 충족되면 재서명 불필요. 결과만 알림. 복구 시각으로 승인 만료나 자료 신선도를 연장하지 않으며, 새로운 승인·자동 arm·주문 재개 권한을 만들지 않음 |
| ② 새 버전 재구성 | 정확 원본은 없지만 온전한 기초 자료로 결과를 다시 계산 가능 → 새 run/revision 생성 → 원본 계보·사용된 재계산기 기록 → 전체 검증/백업 | 기존 승인을 수정본에 적용하지 않음. 새 내용에 필요한 승인을 요청. 과거 자료를 새 전향 관측으로 가장하지 않음 |
| ③ 연구 재실행 | 당시 필수 호가·가격·결정·후보 기록이 없어 과거 결과를 입증할 수 없음 → 새 프로토콜/관측/평가 및 이전 시도 연결 | 다시 다운로드한 거래소 자료를 당시 지연·호가·조회 실패와 같은 원본으로 취급하지 않음. 새 연구·승인 필요 |
| ④ 해당 연구 사용 중단 | 복구·재구성·재실행 불가능 또는 중단 선택 | 이유·잔여 자료·실패 시도 보존, 해당 bundle과 종속 승인/선발 참조를 사용 중단. 무관한 독립 연구는 유지 |

복구 기준은 손상 폴더 안에서 발견한 임의의 공개키/manifest가 아니다. 기존 독립 trust anchor로 검증한 승인 증거와 그 서명 대상 manifest가 기준이다. 백업의 자체 해시만 맞아도 원본이라고 승인하지 않는다. 키 폐기/타협 또는 출처 부정 때문에 기존 승인을 신뢰할 수 없는 경우는 exact-byte 복구로 해결되지 않는다.

### 6. 운용 영향과 보호 보유 연결

- 자료 의존성 인덱스를 두고 `bundle → review → selection → deployment/session` 참조를 추적한다. 공유 원본 하나가 손상되면 그 원본에 의존한 모든 연구를 보류하되 무관한 자료를 전역 중단하지 않는다.
- 영향받은 증거를 이용한 신규 선발·새 진입은 보류한다. 이미 보유한 자산은 별도의 최신 계좌·주문·위험 관측과 유효한 운용 정책으로 감시한다.
- 자료 손상, 저장 장애, 프로그램 재시작 자체를 매도 신호로 쓰지 않는다. 전략 신호나 기존 위험 조건이 입증되었을 때만 해당 매도 경로를 평가한다. 자료가 없으면 `판단 불가`이지 `상승 예상으로 보유`가 아니다.
- 모니터가 실행되어 유효하게 보유 결정을 내린 상태, 감시는 되나 전략 판단이 불가능한 상태, 계좌/호가/주문 경로가 끊겨 아무 주문도 보장할 수 없는 상태를 별도 표시한다.
- 과거 A1 설계 `docs/superpowers/specs/2026-11-12-standing-protective-hold-design.md:26` 및 `:237`, `:243`, `:341`은 확인 실패나 복구를 매도 사유로 두는 부분이 있다. 최신 사용자 요구와 충돌하므로 그대로 재사용하지 않고 보호 보유 개정 설계에서 제거·대체해야 한다. 현재 구현 완료라고 표시하지 않는다.
- 기존 손실 하한·일일 한도·halt·승인 유효기간·보유 자산 대조 요건은 완화하지 않는다. 연구 승인만으로 세션 arm이나 주문 권한을 만들지 않는다.

### 7. 변경 범위와 단계별 검증

예상 변경 범위는 `strategy.py`, `study.py`, `study_review.py`, `review_request.py`, 새 bundle/incident/recovery 모듈 및 CLI/화면, detached approval parser/verifier와 signer 호환 경계다. 패스키 도입은 기존 Ed25519 서명을 가공해 만드는 일이 아니라 별도 버전의 승인 증거와 독립 신뢰 경계 변경이므로 해당 설계와 함께 검토한다. 현재 strict signer는 새 필드를 거절하므로 자동 이식/묵시적 schema upgrade를 금지한다.

1. **입력·후보 결과 검증:** 정당한 탈락 앞/손상된 마지막 프레임 뒤 조합에서 전체 거절; 모든 후보 raw bytes에 공백 하나 변경해도 기존 commitment 불일치; 실패 지표/p값 미생성; prior attempts/전체 가족 수 보존; 벤치마크 실패/no selection.
2. **저장 확정:** 파일별/manifest/게시/catalog/backup 단계마다 crash·disk-full 주입; 중간 bundle 비노출; 같은 ID 동시 게시 충돌; 전체 후보 누락/추가·중복 경로·case 충돌·symlink/junction 거절; 원본/보고서 보존; 대용량은 파일 원본을 삭제하지 않고 streaming hash/분할 저장 구조로 처리.
3. **정확 복구:** 변형/잘린 원본 격리; 신뢰되지 않은 backup/manifest/키 거절; 전체 파일 exact recovery만 성공; 유효 서명은 재서명 없음; 만료/폐기/코드변경/규칙변경은 자동 승인 재생 불가; 결과 알림 실패가 복구 성공 또는 승인으로 바뀌지 않음.
4. **재구성/재실행/중단:** 새 ID와 부모 계보, 기존 버전 보존, 신규 승인 요청, 다운로드한 과거 자료의 출처 분류, 종속 관계별 보류, 실패 후보 삭제 거절.
5. **보유 운용 회귀:** 연구자료 손상만으로 sell/market-order 호출 없음; 독립된 유효 보호 조건은 기존 경로대로 평가; 계좌·미체결 대조 실패 시 실행 불가 상태 표시; 복구/재시작으로 arm·승인 만료가 초기화되지 않음.

테스트는 합성 파일·고정 시간·일회용 키·임시 홈으로만 실행한다. Windows ACL/reparse/rename/충돌 및 iPhone 상호작용은 해당 환경에서 별도 검증해야 한다. 인위적 저장 장애 재현은 실제 계좌 장애 사례로 보고하지 않는다.

### 8. 남은 결정과 이미 확정된 요구

이미 확정되어 재질문하지 않을 것: 원본·정상 호가·보유 내역 보존, 전체 후보군 보존, 손상 후보 삭제 금지, 기존 위험 하한 유지, 손상/재시작 자동 시장가 청산 금지, Telegram은 알림/진입이고 WebAuthn은 별도 승인 증거라는 경계.

배포 전에만 필요한 추가 입력: 비동기화 확정 저장소와 별도 버전 백업 위치/매체, HTTPS 승인 서비스 운영 위치 및 독립 trust anchor 관리·복구 방식. 코드·순수 검증기·가짜 파일 장애 테스트는 이 입력 없이 준비할 수 있다. 동기화 폴더 밖의 검증된 기본 로컬 경로를 제안할 수는 있지만 사용자의 PC에 실제 설정했다고 간주하지 않는다.

이 문서는 코드·저장·승인 절차의 설계 근거다. 실제 연구 성공이나 실전 준비 완료를 주장하지 않는다. 법률, 세무, 투자 조언이 아니며 면허를 가진 자문가가 아니다.

### 2. 사용자 흐름과 권한 분리

1. 독립된 로컬 승인 요청기가 실제 파일·배포·현재 정책에서 불변 요청을 만든다. 일반 TRADEGEN 앱은 요청 제안만 할 수 있으며 스스로 승인 근거를 발행하지 않는다. 로컬 요청기와 HTTPS 서비스 사이에는 사전 등록된 별도 장치 자격으로 인증된 전송을 사용한다. 이 전송 자격은 owner 서명키·거래소 키가 아니고 승인 권한도 아니다. 서버는 요청 대상 owner에 대한 접근 통제를 적용하며 링크를 아는 것만으로 증거 열람·승인 대상을 교체할 수 없게 한다. GET 링크·Telegram callback은 상태 적용을 하지 않고 상태 변경에는 CSRF/session 검증을 적용한다.
2. Telegram에는 요청 종류, 짧은 대상 식별자, 만료 시각, 승인 페이지 진입 링크만 알린다. 링크와 callback은 승인 권한이 아니며 원본 금융 자료·비밀값을 메시지에 싣지 않는다.
3. 사용자는 고정된 HTTPS 승인 사이트에서 대상 버전, 전체 manifest 요약·해시, 승인 범위, 효력/만료, 중요한 변경사항을 확인한다. 표시 데이터는 서버의 고정된 요청 원문에서 생성한다. URL 파라미터·봇 메시지를 승인 본문으로 쓰지 않는다.
4. `navigator.credentials.get`에 `userVerification="required"`를 요청한다. Face ID/기기 암호의 화면과 검증은 iPhone이 담당한다. 브라우저·봇·서버는 생체정보나 기기 암호를 받지 않는다. 웹 내부 화면이 지원하지 않으면 같은 고정 HTTPS origin의 Safari 등 외부 브라우저로 이동한다. Telegram WebView의 성공 여부에 의존하지 않는다.
5. 서버는 등록된 credential과 일회성 challenge를 예비 검증하고 증거를 저장한다. 승인 적용·credential 폐기·이후 권한 사용의 유일한 순서 결정점은 Windows 독립 검증기의 로컬 authority ledger다. 로컬 검증기는 서버의 PASS를 믿지 않고 원본 assertion, 로컬에 등록된 고정 요청/nonce, 현재 registry를 다시 검증해 같은 직렬화 경계에서 정확히 한 번 적용한다.
6. 결과는 `승인 검증됨 / 적용 대기 / 적용 완료 / 만료·거부 / 적용 확인 필요`로 구분한다. PC가 꺼져 있거나 응답이 없으면 `완료`로 표시하지 않는다. 결과 알림 실패는 승인 자체를 반복 적용시키지 않는다.

승인 범위는 적어도 `deployment.code`, `policy.rules`, `policy.limits`, `research.review`, `session.activate`, `authority.enroll`, `authority.revoke`, `authority.recover`로 구분한다. 한 요청은 한 범위만 가진다. 같은 화면에서 묶음 표시해도 각각 독립 요청·challenge·증거·적용 결과를 남긴다. 연구 검토 승인은 세션 활성화, 계좌 설정, 주문·출금 승인을 포함하지 않는다.

### 3. 고정 요청과 WebAuthn 증거 형식

**제안 형식이며 현재 구현이 아니다.** 정확한 필드와 canonical encoder는 별도 계약 테스트로 고정한다.

`ApprovalRequestV1`에는 다음을 포함한다.

- `request_id`, `schema`, domain separator, `owner_authority_id`, `authority_epoch`, `credential_registry_digest`.
- `scope`, 대상 배포/연구/세션 ID·버전, 소스·의존성 manifest hash, 원본 자료 bundle/manifest hash, 후보군 commitment, 정책/위험 계약 hash. 해당하지 않는 필드는 스키마별로 금지하거나 명시적 null만 허용한다.
- `payload`의 canonical bytes 및 digest, `display_schema_version`, 표시 문구의 불변 본문 또는 그 digest. 숫자·날짜·단위·강화/완화 여부는 canonical 데이터에서 직접 렌더링한다.
- `requested_at`, `challenge_expires_at`, `approval_not_before`, `approval_expires_at`, 적용할 현재 owner/control head 또는 그 범위의 단조 증가 epoch.
- 정확한 RP ID와 허용 HTTPS origin, 허용 인증 알고리즘, 요청한 UV 정책.

서버는 최소 32바이트 CSPRNG nonce를 생성하고, `SHA256(domain || nonce || request_digest)`를 challenge로 사용하며 nonce·본문·request ID·상태를 한 레코드에 저장한다. challenge를 사용자에게 발행하기 전에 Windows 독립 검증기의 로컬 ledger에도 동일 request ID·불변 본문·nonce·만료·registry epoch를 등록하고 확인받는다. 서버가 나중에 임의의 challenge와 본문을 제시해도 로컬 미등록 요청이면 거절한다. 단순 랜덤 challenge도 서버 매핑으로 결합할 수 있지만 이번 설계에서는 내용 digest의 결합을 명시한다. 내용 변경 시 동일 request ID/nonce를 재사용하지 않고 새 요청을 만든다.

연구 확정본의 manifest는 새 envelope의 명시적 `bundle_manifest_sha256`와 전체 family commitment에 결합한다. 기존 `audit_sha256`는 사람의 검토 보고서 해시라는 기존 의미를 유지하며 bundle manifest를 대신 넣어 의미를 바꾸지 않는다. v1 서명이 새 manifest를 승인했다고 추정하지 않는다.

`WebAuthnApprovalEvidenceV1`에는 요청 원문/해시, credential ID, raw `clientDataJSON`, raw `authenticatorData`, signature, 반환된 userHandle, 당시 registry revision 및 검증 정책 버전을 보존한다. 등록 시 획득한 COSE 공개키·알고리즘·RP ID·소유자 매핑·폐기 상태는 별도 registry에 둔다. 본인 확인에 필요한 증거를 보존하되 credential 공개키도 개인 식별 자료로 취급하고 공개 GitHub에 올리지 않는다.

검증은 검증된 WebAuthn 라이브러리를 사용하고 다음을 모두 확인한다.

- `clientData.type == webauthn.get`, 정확한 challenge, 허용된 origin의 완전한 일치, expected RP ID의 `rpIdHash`. 다른 서브도메인·HTTP·임의 port를 암묵 허용하지 않는다. `crossOrigin`/`topOrigin`은 이번 top-level 승인 흐름 정책에 맞지 않으면 거절한다.
- credential이 현재 owner와 허용된 scope에 등록되고 폐기·유예 상태가 아닌지, userHandle이 반환되면 정확히 같은 소유자인지. 반환이 없는 경우에도 credential ID 매핑으로 소유자를 확인한다. Telegram 사용자 ID만으로 이 매핑을 만들지 않는다.
- UP와 UV 플래그, COSE 알고리즘 allowlist, `authenticatorData || SHA256(clientDataJSON)`에 대한 정확한 서명. 예상하지 않은 extensions·잘못된 길이·중복 JSON 키·비표준 인코딩은 고정 오류로 거절한다.
- 요청 만료·미래 시간·시계 역행, 승인 범위/자료/배포/현재 권한의 일치, 사용·폐기된 request/challenge 여부를 적용 직전에 다시 확인한다.
- BE/BS(백업 가능/백업 상태) 플래그 일관성을 저장·검증한다. `signCount`는 보조 위험 신호로 다루며 동기화 패스키에서 0 또는 비단조 카운터가 있을 수 있다. **모든 패스키에 양수 증가 카운터를 강제하지 않으며**, 반대로 카운터만으로 재사용을 허용하지 않는다. 재사용 차단은 서버/로컬의 일회성 요청 기록과 서명 결합으로 보장한다.

WebAuthn의 UV는 사용자가 장치에서 인증됐음을 증명하며, Face ID인지 암호인지를 서버가 확정하거나 사용자가 문서를 읽었다는 것을 암호학적으로 증명하지 않는다. 동기화 패스키는 특정 iPhone 한 대의 사용 증거가 아니다. 승인 사이트가 악성 코드를 표시하는 위험까지 UV가 해결하지 않으므로 origin·사이트 배포·표시 renderer 또한 신뢰 경계의 일부다.

### 4. 정확히 한 번 적용·폐기의 단일 순서와 장애 처리

**권한 상태의 유일한 원장은 Windows 독립 검증기의 로컬 authority ledger다.** 서버 DB의 인증 성공/폐기 요청 시각이나 캐시된 epoch는 이 원장의 확정 상태가 아니다. 서버와 PC 사이에 분산 트랜잭션이 있다고 가정하지 않는다. `apply`, `revoke`, `authorize_use`는 모두 이 로컬 원장의 같은 직렬화·트랜잭션 경계에서 순서를 정한다.

요청 상태는 `pending → evidence_received → local_verified → applying → applied` 또는 `expired/rejected`다. 폐기는 별도로 `폐기 요청됨 → PC 적용 대기 → 폐기 적용 완료`를 표시한다. 서버가 증거를 저장했다는 이유만으로 `local_verified/applied`를 표시하지 않는다.

- 서버는 challenge 응답 접수 여부와 원본 assertion 저장을 한 트랜잭션으로 확정한다. 같은 응답 재전송에는 기존 증거 접수 결과만 돌려준다. 이 기록 자체는 권한 부여가 아니다.
- 로컬 검증기는 등록된 요청/nonce 및 완전한 원본 WebAuthn assertion을 현재 로컬 credential registry·target bytes·만료·owner/control head에 대조한다. `request_id + evidence_digest`를 중복 적용 방지 키로 쓰고, 같은 원장 트랜잭션에서 사용 처리·권한 효과·확정 영수증을 기록한다. 원장 밖 파일 변경이 필요하면 준비/완료 기록과 재시작 대조가 끝날 때까지 그 효과를 사용 가능하게 공개하지 않는다.
- 폐기 역시 원본 패스키/독립 recovery 증거를 로컬에서 검증한 뒤 같은 원장에 `revoke`를 확정한다. 로컬 확정 시 해당 credential과 미사용 요청·미적용 증거를 무효화하고 epoch를 올린다. `revoke`가 `apply`보다 먼저 확정됐으면 그 적용은 거절한다. `apply`가 먼저 확정됐더라도 뒤의 폐기는 해당 승인에 의존하는 **이후 사용**을 차단·재평가한다. 이미 집행된 효과·체결을 되돌리거나 과거 기록을 삭제하지 않는다.
- 승인 소비자는 오래된 `approved=True`/캐시 epoch로 행동하지 않는다. 각 코드 활성화·정책 적용·전략 선발·신규 진입/주문 dispatch의 권한 사용 직전에 `authorize_use`를 같은 로컬 원장에 요청해 현재 폐기 상태와 대상 결합을 확인한다. 적용/폐기/사용의 경합 순서를 이 한곳에서 기록한다. 큐에만 있고 아직 dispatch가 승인되지 않은 효과는 폐기 후 실행하지 않는다. 이미 외부 전송이 시작된 작업은 없던 일로 만들지 않고 결과를 조회·대조한다. 거래소 체결까지 로컬 원장과 원자적이라고 주장하지 않는다.
- 서버는 폐기 요청을 접수하면 해당 credential의 새 인증 증거 발행/접수를 즉시 거부할 수 있다. 그러나 로컬 확인 영수증 전에는 전역 폐기 완료라고 알리지 않는다. 기존 전달 중인 증거와 폐기 요청이 경합하면 원격 요청 시각이 아니라 위의 **로컬 확정 순서**가 효력 순서다. 이를 UI·감사 기록에 명시한다.
- Windows가 꺼져 있거나 통신이 끊겼으면 `폐기 요청됨 / PC 적용 대기`다. 새 승인 적용 경로는 fresh 요청/전달·상태 확인을 하지 못하면 보류한다. 과거 캐시를 근거로 폐기와 원자적 순서를 확보했다고 간주하지 않는다. 재연결 시 미처리 폐기·복구 사건을 수신·검증하고 상태를 대조한 뒤 새 승인 적용을 재개한다.
- 이미 접수된 승인을 PC 재시작 후 이어 적용하려면 현재 원장, 미사용 nonce, 유효기간, 대상 bytes와 계좌/정책 전제를 다시 확인한다. 만료나 대상 변경이면 새 요청이 필요하다. 결과 통지 유실은 기존 로컬 영수증·target 상태 대조로 해결하고 주문 재전송·재무장으로 확인하지 않는다.
- 보류는 해당 credential/authority epoch 및 target 의존 범위에 한정한다. 별도 유효 권한과 증거를 가진 연구까지 자동 보류하지 않는다. 공통 root에 실제로 의존하는 범위만 함께 영향을 받는다. 승인 서비스 연결 장애를 기존 승인 전체의 소급 폐기로 취급하지 않는다. 기존 보유 자산 관리는 현재 유효한 별도 보호 관리 권한·기존 위험정책에 따라 계속하거나 명시적 관리 불가 상태로 알리며 자동 청산하지 않는다.
- Telegram 알림 유실·미응답은 승인 또는 폐기의 완료가 아니다. outbox는 알림을 재시도하며 링크는 로컬 확정 영수증 여부를 포함한 최신 확인 상태를 표시한다.

기본 제안은 일회성 인증 요청 유효시간 5분이다. 이 값은 승인 효력 기간과 다르다. 전략 검토는 기존 24시간 최대 및 연구 자체 review deadline 중 더 이른 시각을 유지한다. 코드/규칙/한도/활성화의 효력 기간은 각 범위 정책으로 명시하고, 최초·완화 한도는 기존 다음 KST 날짜 규칙을 유지한다. 초기 운영의 정확한 각 범위 만료값은 정책 설정으로 정하며 미설정이면 해당 요청을 발행하지 않는다.

### 5. Ed25519에서의 안전한 전환과 자기 승인 방지

**패스키는 기존 Ed25519 소유자 서명을 생성하지 않는다.** 서버가 owner 개인키를 보관해 WebAuthn 성공 후 대리 서명하는 우회 구조는 사용하지 않는다. 봇에는 owner 개인키·거래소 주문키를 주지 않는다.

권장 전환 구조는 다음과 같다.

1. 현재 독립 signer/소유자 신뢰 root를 실제로 가지고 있는지는 사용자 측에서 확인한다. 이 검토는 실제 owner 홈을 읽지 않았으므로 이미 등록됐다고 가정하지 않는다.
2. 새 독립 bootstrap/검증기 패키지를 저장소 밖·별도 ACL·별도 배포 경로에 설치한다. 소유자가 최초 릴리스 해시·의존성·동작을 독립 확인한다. 새 TRADEGEN 앱이 자신과 검증기 hash를 제출했다고 신뢰하지 않는다. 운영 시에는 TRADEGEN 프로세스가 검증기 실행 파일·공개 root·registry·적용 journal을 고칠 수 없는 별도 OS identity/ACL 경계를 사용한다. 단순히 같은 사용자 권한으로 다른 폴더에 복사하는 것만으로 악성 대상 코드에 대한 격리가 된다고 주장하지 않는다.
3. 최초 등록은 현재 신뢰 root가 새 verifier release/closure, 정확한 origin/RP ID, credential registry digest, scope allowlist, authority epoch, 복구 root와 전환 기준 owner head를 결합한 detached `ApprovalAuthorityGrantV1`을 승인하도록 설계한다. 현재 signer CLI에는 이 형식이 없으므로 별도 독립 migration utility가 필요하다. 최초 setup에서만 현 소유자의 독립 확인이 남을 수 있고, 일반 승인은 이후 패스키 UI로 처리한다.
4. 새 verifier는 공개 root와 승인된 grant를 별도로 pin하고 WebAuthn 증거를 직접 검증한다. 검증 대상 TRADEGEN 릴리스는 grant/registry/root를 자체 교체할 수 없다. verifier의 신규 버전 또는 root/등록 origin 변경은 기존 검증기에 의해 자동 승인하지 않고 독립 recovery/bootstrap 권한의 별도 승인 경로를 거친다.
5. v1 owner 로그·anchor를 바이트 그대로 유지한다. v2 승인 journal의 genesis는 마지막 검증된 v1 head 및 신규 authority grant에 연결한다. v2에는 새로운 domain/schema와 WebAuthn 원본 증거 reference가 있으며 기존 `sig`를 가장하지 않는다. v1/v2 검증 후 생성한 내부 인증 결과만 기존 정책 reducer의 의미에 연결한다.
6. 전환 시 모든 active session을 재평가하고 기존 halt·더 높은 보호 하한·한도 발효일·철회 상태를 보존한다. v1와 v2 owner 이벤트의 동시 작성은 허용하지 않는다. cutover head/epoch를 지나 legacy owner 이벤트가 추가되면 자동 합치지 말고 무결성 사건으로 보류한다. system halt/disarm 등의 이후 기록과 함께 하나의 명확한 순서를 보장하는 v2 이벤트 계약이 선행되어야 한다.
7. 되돌리기는 자동 downgrade가 아니다. 기록된 전환/철회 상태를 보존하고 독립 recovery 승인과 새 epoch를 요구한다. 과거 정상 로그를 복사해 새 승인·폐기를 잊게 할 수 없어야 한다.

기존 코드만으로 v2를 받아들일 수는 없다. `core/compliance/owner.py`, owner context/authority, review_auth/study_review, control session verification 및 독립 signer와 대응 검증 테스트까지 변경 범위에 포함한다. 첫 PR5 outcome 개선과 한 PR에 몰아 넣지 않고 별도 단계로 배포한다. 패스키 도입 전까지 기존 Ed25519 검증 경로를 유지하며, 미구현 패스키 증거를 legacy 서명으로 받아들이지 않는다.

### 6. 최초 등록·분실·폐기·복구

- 최초 등록: 고정 HTTPS 사이트의 등록 challenge → 장치 UV → attestation/credential 구조 및 등록 origin/RP ID 검증 → 소유자와 공개키 결합 → 독립 bootstrap 승인 → registry 확정. Telegram 계정만 가지고 최초 등록할 수 없다. attestation을 기기 독점의 증거로 사용하지 않는다.
- 추가 등록: 기존 유효한 소유자 패스키의 `authority.enroll` 승인 또는 별도 offline recovery root 승인으로 진행한다. 등록 대상 새 공개키·허용 scope·registry 변경 hash를 승인 화면에 고정한다.
- 기기 분실: 사용 가능한 다른 등록 수단 또는 offline recovery root로 `authority.revoke`를 요청한다. 서버는 새 증거를 차단하고, Windows 독립 검증기의 로컬 원장에 폐기가 확정될 때 해당 credential·미사용 challenge·미적용 승인을 폐기하고 epoch를 올린다. PC 미연결이면 `폐기 요청됨 / PC 적용 대기`로 표시한다. 이미 집행된 승인/주문을 삭제하지 않고 이후 의존 권한 사용을 재평가한다.
- 동기화 패스키의 한 기기만 사라진 경우 RP는 그 iPhone 한 대만 특정해 폐기할 수 없을 수 있다. 필요하면 그 credential 전체를 폐기하고 Apple 계정/기기 분실 보호와 새 등록을 병행한다. 기기 한 대 독점이 필요하면 별도 기기 제한 인증수단 설계가 필요하며 현재 범위에 있다고 가정하지 않는다.
- 모든 패스키를 잃은 경우 미리 보관한 offline recovery root와 검토된 recovery utility를 사용해 전체 관련 credential·미적용 승인을 폐기한 뒤 새 epoch에서 등록한다. recovery root도 없으면 Telegram/이메일/임의 DB 수정만으로 우회하지 않고 새로운 독립 초기 신뢰 설정 및 관련 승인 재수립을 요구한다.
- 복구 절차는 자동 무장·한도 완화·halt 해제·주문 실행을 포함하지 않는다. credential 폐기 이후 과거 연구 서명 재사용 가능성도 당시 승인 조건/현재 철회 정책에 따라 검증한다. 손상본의 정확한 복구라도 폐기된 권한을 되살리지 않는다.

### 7. 연구 파일 복구와 알림 연결

정확히 같은 manifest/원본 hash로 자동 복구한 경우 기존 승인 원문과 WebAuthn/Ed25519 증거, 유효기간, 현재 폐기 상태 및 다른 승인 조건을 재검증한다. 통과하면 재서명 없이 `원본 복구·재검증 완료`만 통지한다. 복구에 실패했거나 승인이 만료됐다면 `복구됨`과 `사용 가능`을 구분한다.

계산을 다시 한 새 버전·새 관측·수정 보고서에는 새 연구/버전·manifest·request ID를 만들고 새로운 승인을 요청한다. 탈락/실패 후보도 전체 manifest와 family commitment에 남는다. 피해 자료에 의존하는 연구·승인만 보류한다. 이미 보유 중인 자산에는 해당 연구의 신규 진입 권한과 보호 보유 관리 권한을 구분해서 적용하며 데이터 손상만으로 시장가 청산하지 않는다.

### 8. 핵심 검증 항목과 구현 단계

| 단계 | 구현/검증 범위 | 완료 기준 |
|---|---|---|
| A. 순수 계약 | request/evidence/registry/grant 스키마, canonical encoding, scope·expiry·digest 검증 | 단위/시간/버전 변경, 중복 키, 누락·초과 필드, 다른 family/manifest, malformed bytes 전부 거부. 코드 승인/연구/활성화 scope 상호 전용 불가. |
| B. WebAuthn 검증 | 가짜 RP와 일회용 credential로 서버·로컬 검증 | 잘못된 origin/RP ID/owner/알고리즘/UV·UP, 폐기키, 만료·재사용·내용 변경, challenge 재결합 모두 거부. 동기화 BE/BS 및 0 counter 정상 사례 유지. 실제 iPhone 동작은 별도 기기 검사로 보고. |
| C. 신뢰 전환 | 독립 bootstrap·v1→v2 journal·폐기/복구 | 대상 앱이 자신을 승인하거나 root/registry/verifier를 대체하지 못함. cutover 후 legacy 추가, 로그 rollback, 새 grant를 옛 epoch에 붙이기, halt/하한 유실 거부. |
| D. 원자 적용·폐기 | 서버 증거 저장 + 단일 Windows authority ledger/outbox | 모든 쓰기 경계의 crash, 동시 클릭, 응답 유실, apply/revoke/authorize_use 순서 양방향, 서버에만 폐기 접수된 단절, PC 재연결에서 최대 1회 적용. 서버 접수/로컬 검증/적용/폐기 대기를 구별. 캐시 epoch로 경합 검사를 대체하지 못함. |

새 설계 테스트의 PASS를 현재 기능으로 보고하지 않는다. 현재 수행한 것은 정적 코드 대조뿐이며 위 자동화·iPhone 실기기·통합 검사는 아직 실행하지 않았다.

### 9. 추가 결정/환경 정보만 남기는 질문 후보

이미 확정된 손실 하한, 정상 호가 보존, Telegram 클릭만으로 승인하지 않음, Face ID/기기암호의 기기 내 처리, 범위별 승인 분리, 원본 복구 시 조건부 재서명 생략은 다시 묻지 않는다.

1. **HTTPS 승인 서비스 운영 장소와 고정 도메인/RP ID**: 운영자가 관리하는 별도 호스트·고정 도메인을 권장한다. 임시 tunnel URL이나 수시 변경 주소를 passkey RP로 고정하지 않는다. 아직 없으면 fixture 서버·계약/UI 개발은 계속하고 실제 등록만 보류한다. 실제 hostname/IP/배포 계정은 공개 로그에 쓰지 않는다.
2. **최초/비상 복구 신뢰 수단**: 기존 독립 Ed25519 소유자 root를 offline bootstrap/recovery 전용으로 유지하는 안을 권장한다. 실제 root가 아직 없거나 분실됐으면 독립 초기 설정 절차가 달라진다. 이 선택은 봇에 개인키를 맡기는 승인이 아니다.
3. **범위별 승인 만료값**: 단기 challenge 5분, 전략 검토 기존 최대 24시간은 제안 기본값이다. 코드·규칙·한도·세션 만료의 구체값은 기존 효력 의미를 유지하면서 운영 정책에서 결정해야 한다. 이 값 미정으로 순수 검증기/저장/전환 테스트를 막지 않는다.

### 10. 표준 참고와 확인 한계

- W3C Web Authentication Level 3: https://www.w3.org/TR/webauthn-3/ — RP ID/origin/challenge, assertion 검증, UP/UV, BE/BS·signCount 개념의 표준 참고.
- Apple Platform Security, Passkeys security: https://support.apple.com/guide/security/passkeys-security-sec8a7f1d1b7/web — Apple 기기 인증·동기화 패스키의 참고.

이번 Cloud에서 위 두 문서의 최신 본문 가져오기는 네트워크 정책의 403으로 실패했다. 따라서 최신 Apple/Telegram/iOS 조합 지원을 실측·확인했다고 주장하지 않는다. 구현 전 공식 표준 버전과 선택할 WebAuthn 라이브러리를 고정·검토하고, 대상 iPhone/Safari/Telegram 조합에서 별도 수용 검사를 수행한다.

이 문서는 소프트웨어 설계 검토이며 법률, 세무, 투자 조언이 아니며 면허를 가진 자문가가 아니다.

## C. 통합 계약과 구현 순서

1. **P5-1 후보 결과:** 전체 원본 검증을 공통화하고 정상 계산 결과/정당한 평가 실패/손상을 구분한다. 실패 후보도 family와 prior-attempt 계산에 남긴다.
2. **P5-2 확정 증거:** 새 bundle manifest와 전용 staging/sealed/catalog, 버전 백업을 구현한다. 목적지 전체 재검증 뒤 catalog에 공개하며 서명·백업·현재 조건 전에는 승인 상태가 아니다.
3. **P5-3 복구:** 사건 격리, 정확 원본 복구, 새 버전 재구성, 새 관측 재실행, 사용 중단을 구현한다. 정확 복구로 승인 만료·자료 신선도·arm 상태를 연장하지 않는다.
4. **A-1 승인 계약:** request/evidence/registry/grant의 새 스키마와 순수 검증기를 테스트한다. 운영 hostname이나 실키 없이 fixture로 개발 가능하다.
5. **A-2 독립 신뢰·적용:** bootstrap 도구, v1/v2 전환, 로컬 권한 journal과 폐기·재사용 방지·복구를 구현·검토한다. 승인 대상 프로그램이 자신의 root나 verifier를 교체할 수 없어야 한다.
6. **A-3 화면·알림:** 고정 HTTPS 승인 페이지·외부 Safari 전환·Telegram outbox를 연결한다. 알림 실패는 승인/적용 성공이 아니다. iPhone 및 Windows 실제 환경 검사는 별도 표기한다.
7. **A-4 범위별 통합:** 코드, 규칙, 한도, 연구 검토, 거래 활성화를 각각 연결하고 기존 게이트 전체를 회귀 검사한다. 하나의 거대 PR로 묶지 않고 각 단계의 검증·검토 후 진행한다.

manifest의 `files[]`는 서명 대상 evidence payload와 보고서 파일의 닫힌 집합이다. **manifest 자기 자신, detached approval, 가변 backup/incident catalog는 포함하지 않는다.** manifest의 canonical bytes를 외부 승인에서 hash로 결합해 순환 참조를 피한다. 이는 필수 evidence를 생략해도 된다는 뜻이 아니다. 백업은 manifest·payload·detached approval을 함께 보존하되 각각의 의미와 hash를 구분한다.

확정본에는 `STAGING → PENDING_VERIFY → VERIFIED_UNAPPROVED → APPROVED_USABLE`의 상태를 둔다. 마지막 상태도 영구 권한이 아니며 사용 시점의 폐기·만료·코드/정책 조건을 다시 검사한다. staging/중단 시도/미완성 복사본은 reader에 정상 연구로 노출하지 않는다.

### 남은 입력과 결정

- **지금의 설계·가짜 데이터 검증에 필요하지 않은 배포 입력:** 비동기화 확정 저장소와 별도 버전 백업 매체, 고정 HTTPS 도메인/RP ID 및 운영 장소, 소유자 독립 root의 실제 보유 여부·복구 수단. 지금 비밀키·계좌·개인 경로를 채팅으로 보내지 않는다.
- **권고 전환안:** 기존 독립 Ed25519 root를 offline bootstrap/recovery 용도로 유지하고, 일반 승인만 WebAuthn으로 분리한다. 실제 root 존재는 미확인이다. 최초 독립 신뢰 확인은 필요하며 일상 승인마다 PowerShell 입력을 요구하는 방식은 대체한다.
- **효력 설정:** challenge 5분은 제안 기본값이고 기존 연구 검토 최대 24시간 등 현재 제한을 늘리지 않는다. 범위별 효력·만료는 기존 정책에 연결하고 누락 시 해당 요청 발행을 보류한다.
- **보유 기한 E 결정 완료:** 사용자는 “기한만으로 매도하지 않고 새 관리 승인 요청”을 선택했다. 신규 진입 중지·갱신 요청으로 처리하며 유효한 기존 관리 권한만 사용한다. 권한 만료 시 자동 주문 없이 읽기 감시/알림·인계 상태이고 연구·보호 매도 권한을 자동 연장하지 않는다.
- **PLB:** 사용자는 floor_state_check 미실행을 확인했다. S1~S12를 임의로 통과 처리하지 않는다. 실제 상태 결과를 요구하는 PLB 분기만 대기하며 위 설계/검증 준비를 막지 않는다.

이번 요구는 설계·단계별 개발 방향이며 실제 서명·계정 연결·Telegram 발송·배포·무장·주문 승인이 아니다. 설계 검토와 소프트웨어 검증을 실제 수익·전략 적격성·실거래 준비 완료와 구분한다.
