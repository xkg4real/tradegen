## 구체적인 변경과 주문 영향

- 큰 원본은 해시로 검증하는 분할 객체에 보존하고 journal에는 작은 참조를 남긴다. 정상 호가를 None으로 바꾸지 않고, 기존 첫 fallback의 정상 flags/tickers 폐기도 새 형식에서 제거한다. 보유 내역·호가·전략 입력은 저장 크기 때문에 바뀌지 않는다.
- 기존 v1/v2 기록·서명을 덮어쓰지 않는다. 새 형식은 새 identity/window에서 사용한다. 저장 한도·쓰기 장애는 명시적 저장 오류이며 조회 실패나 매도 신호로 변환하지 않는다.
- 보호 상태는 **전략 HOLD / 판단 불가 / 실행 불가**를 구분한다. 오류·재시작·설정 누락만으로 매도하지 않는다. 유효한 전략·기존 위험 조건과 유효한 주문 권한이 있어야 매도를 계획한다. 기존 halt 우선순위도 유지한다.
- 매도는 검증된 Upbit 원화 현물의 기존 지정가 IOC 경로에 연결한다. 부분체결·미체결·UNKNOWN·잔량을 대조하며 시장가 전환이나 손실 하한 완화는 없다.
- **이번 실험:** 정상 원본 279531바이트(기존 fallback 뒤에도279312바이트)를 무손실 복원하는 별도 모델 15 PASS /0 FAIL. 실제 계좌 장애, 운영 통합, Windows 전원장애, 실제 주문 검증은 아니다.

### 2. 제안: 검증되는 내용 주소 객체 + 작은 v3 journal 참조

#### 2.1 보존 대상과 계층

- 논리 슬롯 자료는 기존 fallback **이전** 값을 사용한다. 모든 보유 내역·계좌 anchor·호가 receipt 원본 bytes·정상 flags/tickers 파싱값과 원본 해시·snapshot·allow·reasons·events·choice를 보존한다.
- 정상 조회 결과를 저장 사정으로 `unavailable`로 바꾸지 않는다. 저장 전후 전략 입력과 결정은 동일해야 한다. 가격·수량·시각의 정밀도를 줄이지 않는다.
- 논리 슬롯을 canonical encoding으로 직렬화하고 `logical_sha256`와 바이트 수를 계산한다. 큰 자료는 정해진 최대 청크 크기로 나눈다. 청크의 순서·길이·내용 해시는 manifest에 고정한다.
- 내용 주소에는 형식·도메인 구분자를 포함한다. manifest 해시와 logical payload 해시는 별도로 둔다. 기존 receipt의 거래소 raw body SHA-256은 바꾸지 않는다.
- 작은 v3 journal 행은 전체 payload를 복제하지 않고 manifest의 해시, 자료 길이, 슬롯 번호 및 형식 정보를 참조한다. 기존 `prev_sha256`/`row_sha256` 연결과 독립 head를 유지한다. journal 행은 기존 262144바이트 상한 안에 있어야 한다.
- 저장 위치는 명시적으로 설정한 state root 아래 전용 object store로 한다. 객체 파일 경로는 검증된 해시에서만 계산하고 임의 경로를 받지 않는다. symlink/reparse point/경로 탈출/비정상 hardlink·동시 교체 방지를 포함한다.
- flags/tickers raw body 자체를 추가 보존하려면 `FlagRead`/`TickerRead`의 전달 계약과 수집 경로까지 변경해야 한다. 현재 파싱값+해시를 raw body 보존이라고 표시하지 않는다. PR5 확정 연구 묶음에는 필요한 원본 수집 evidence를 포함하고, 이미 소실된 과거 raw body를 만들어 넣지 않는다.

#### 2.2 상한과 용량 사전 확인

- 청크 크기·전체 논리 payload 한도·manifest 항목 수·한 window의 총 byte/object 한도를 분리한다. 모두 manifest/schema와 검증기에 반영한다.
- 초기 실험은 청크 65536바이트, 논리 payload 16MiB를 사용했다. 이는 **실험 파라미터**이며 운영 한도로 승인되거나 성능 검증된 값이 아니다.
- 운영 한도는 실제 허용 계좌/시장 입력의 최악 크기, window 길이, 저장 매체 여유·저장 시간 측정을 통해 정한다. 기존 16MiB 연구 capture 한도와 live history 논리 슬롯 한도를 혼동하지 않는다.
- window 시작 전에 필요한 저장 공간·권한·동일 volume의 임시 확정 지원 여부·총량 예산을 검사한다. 슬롯마다 직렬화된 실제 크기와 쓰기 여유도 검사한다. 사전 여유 검사는 후속 `ENOSPC`를 예방할 수 있지만 보장하지는 못한다.
- 허용 범위를 넘거나 실제 저장이 실패하면 명시적인 **저장 용량/저장 장애 상태**를 남긴다. 호가 유효성 실패로 위장하거나 자료 일부를 자르지 않는다. 거래를 무조건 진행하는 보장도 하지 않는다.
- 단순 admission 거부는 journal/head/전략 메모리 변경 전에 결정한다. 저장 중 장애는 아래 절차에 따라 미확정 객체가 남을 수 있으나 확정된 슬롯으로 취급하지 않는다.

#### 2.3 확정 순서와 중단 복구

단일 writer lock 및 기존 journal → head 잠금 순서를 유지한다. 다른 프로세스가 같은 객체를 쓰는 경우까지 검사해야 한다.

1. 전체 논리 자료를 검증하고 정규 직렬화·상한·manifest를 준비한다. 아직 전략 상태를 갱신하지 않는다.
2. 같은 volume의 임시 파일에 청크를 모두 쓰고 flush/fsync한다. 길이·해시를 재검사한 뒤 이름을 확정한다. 존재하는 같은 해시 객체는 내용을 확인하여 재사용하되 덮어쓰지 않는다.
3. 모든 청크를 읽어 검증한 manifest도 동일하게 확정한다. manifest 확정 전에 journal 참조를 발행하지 않는다.
4. 작은 journal 참조 행을 append+fsync한다. head successor 검사는 tail 행 해시뿐 아니라 v3 객체 graph의 완전성도 검사한다.
5. 독립 head를 compare-and-set하고 readback을 확인한다.
6. 그 후에만 슬롯 수·chooser state·allow·메모리 head를 확정한다. 주문 경로는 이 확정 결과를 사용한다.

| 중단 위치 | 재시작 시 처리 |
|---|---|
| 임시 파일/일부 청크만 존재 | 아직 확정 슬롯 아님. 임시/미참조 자료로 격리하고 기존 head에서 시작. 가짜 슬롯·None 호가로 채우지 않음 |
| manifest 완성, journal 행 없음 | 미참조 객체. head를 바꾸지 않음. 보존/정리 정책에 따라 별도 처리 |
| journal append 완료, head 미확정 | 현 계약처럼 head 불일치로 중단. 단순히 journal tail을 새 head로 채택하지 않음. 별도 승인된 reconciliation 없이는 재개 불가 |
| head 확정, 메모리 갱신 전 | head에 연결된 전체 객체를 검증하여 재생. 하나라도 손상/누락이면 해당 history 사용 보류 |
| 확정 객체 누락/변조 | 정확한 해시 원본 백업으로 복원하고 전체 참조 묶음 검증. 새로운 조회 값을 과거 receipt로 삽입하지 않음 |

기존 missed-slot/창 만료 규칙을 몰래 바꾸지 않는다. 장애 중 실제 슬롯 시간이 지나갔다면 원래 창의 정상 재생에 성공해도 누락 관측을 소급 생성할 수 없다. 신규 진입 중지와 보유 자산 감시·매도 판단은 보호 보유 설계의 별도 상태에 연결한다.

파일 rename의 원자성은 디스크 전원 장애 내구성이나 여러 파일+head의 원자적 transaction과 다르다. Windows에선 파일 flush·동일 volume 확정·crash recovery 검증이 필요하다. 디렉터리 fsync를 호출했다고 간주하지 않는다. 검증되지 않은 저장 매체나 OneDrive 동기화 폴더를 확정 증거 저장소로 사용하지 않는다.

#### 2.4 재생과 검증 경계

- v3 참조 → manifest → 순서가 고정된 모든 청크 → 전체 bytes 길이 및 논리 해시 → 기존 논리 슬롯 schema/receipt/계좌/보유/전략 검증 순서로 읽는다.
- 누락된 청크, 중복/잘못된 인덱스, 길이 오류, 해시 불일치, manifest 교체, 과도한 청크 수, 다른 window/slot의 객체 끼워 넣기 모두 그 자료를 사용하는 슬롯·history를 거절한다.
- 각 trust boundary에서 실제 읽은 bytes의 해시를 확인한다. 파일명·mtime·이전 캐시 값만으로 변조 방지를 주장하지 않는다. 검증한 메모리 bytes와 실제 전략 입력을 동일하게 사용하여 검사 후 파일 교체 문제를 막는다.
- 정상적으로 기록된 조회 실패는 정확한 실패 상태/원인을 그대로 보존한다. 저장 객체가 사라진 것을 조회 실패로 변환하지 않는다.
- snapshot/시장 raw자료의 digest는 진위 provenance의 전부가 아니다. 현재 독립 head의 신뢰 한계(프로그램과 head를 함께 바꿀 수 있는 공격자)는 이 저장 변경만으로 해결되지 않는다.

#### 2.5 기존 형식과 승인 호환

- 기존 v1 고정종목 및 v2 유니버스 기록은 원본 bytes, row hash, golden digest를 변경하지 않고 읽는다.
- 기존 v2의 첫 fallback이 이미 버린 flags/tickers는 복구되었다고 주장하지 않는다. 해당 시점의 신뢰 가능한 원본 백업 없이는 재구성 불가능하다.
- 기존 승인 window의 history를 제자리에서 v3로 다시 쓰지 않는다. v3 writer는 코드/형식 승인을 포함한 새 identity와 새 window에서 시작한다. 저장 형식 revision을 identity/프로토콜에 명시한다.

### 4. 작은 구현 단계와 통과 기준

1. **저장 계층**: v3 codec/object store/형식 binding/무손실 payload 연결. 현 first fallback 제거. 정상 입력의 전략 결정·호가·모든 보유 내역 동일성, 각 chunk/행/총량 경계, 기존 v1/v2 golden, no-overwrite, 경로·동시성 검증을 통과한다.
2. **확정과 재시작**: journal/head 연결 및 crash fault injection, 손상 객체·불완전 commit 분류, 백업 exact restore, 미확정 채택 금지, 누락 슬롯 보류를 검증한다. Windows 파일 교체/잠금/재시작 시험은 Linux 결과와 따로 기록한다.
3. **보호 보유 상태 전이**: 진입 중지·모형의 유효한 보유 결정·판단 자료 미비·실행 불능을 구분한다. 저장 실패/재시작을 매도 신호로 취급하지 않는 검증을 추가한다. 기존 하한/손실 정책 유지.
4. **매도 연결**: 유효한 전략/위험 신호, 신뢰 가능한 계좌·미체결 대조, 유효 호가·가격/수량/체결 정책, 실행 journal의 작동 여부를 검증한 뒤에만 주문 계획을 만든다. 부분체결·미체결·응답 불명확을 각각 검증한다. 이 단계도 실제 주문이 아닌 테스트부터 수행한다.

시뮬레이션 저장 장애만으로 보호 매도의 운영 가능성이 입증되지는 않는다. 저장 장애가 주문 journal까지 영향을 주면 중복 주문과 체결 추적을 보장할 수 없으므로 '모형이 보유를 선택'한 상태로 표시하지 않고 실행 불능을 알린다. 대체 저장소/긴급 종료권한은 별도 설계 없이 자동 추가하지 않는다.

- 정상 호가·보유 내역 보존, 오류만으로 즉시 매도하지 않음, 손실 하한 유지, Upbit KRW 현물 범위는 이미 확정된 요구다. 다시 묻지 않는다.

- 새 v3 기록과 기존 승인 창 전환은 코드 승인 범위에 포함한다. 현재 사용자 지시를 실서명·실거래 활성화 승인으로 해석하지 않는다.

법률, 세무, 투자 조언이 아니며 면허를 가진 자문가가 아니다.

### 3. 상태 모델

하나의 `hold` 문자열에 판단·통신·실행 상태를 섞지 않는다. 최소 세 축을 분리한다.

1. **전략 결과:** `HOLD`, `SELL`, `UNAVAILABLE`. HOLD는 유효한 입력으로 실제 계산한 결과일 때만 사용한다. 준비 구간·증거 손상·예외는 UNAVAILABLE이다. 보호 보유에서는 BUY나 종목 교체의 매수 절반을 실행하지 않는다.
2. **관리 상태:** `MONITORING`, `RECOVERING`, `WAITING_INPUTS`, `EXIT_PENDING`, `HALTED`, `OWNER_ACTION_REQUIRED`, `DUST`, `CLOSED`. 각 상태는 마지막 정상 관측·이유·적용 코드/정책/연구 버전을 가진다.
3. **실행 가능성:** `can_observe`, `can_evaluate_strategy`, `can_evaluate_risk`, `can_record`, `can_reduce`, `can_enter`와 각각의 고정 사유 코드. `can_enter=false`가 `can_reduce=false`와 동의어는 아니다.

예: 정상 전략 HOLD이면 “유효 자료로 보유 판단, 마지막 판단 시각 …”. 조회 불가이면 “보유 중 / 판단 불가 / 신규 진입 차단 / 자동 매도 현재 불가”. 위험 조건이 확인됐으나 주문 경로가 막혔으면 “보호 매도 조건 확인 / 실행 불가 / 사유 …”. 후자의 손실 보호를 완료나 매도 완료라고 표시하지 않는다. PC 전원·프로세스가 꺼졌다면 모니터링 중이라고 표시하지 않는다. 재연결 시 마지막 heartbeat와 관측 시각을 드러낸다.

상태 전이 우선순위는 기존 halt/소유자 종료 → 계좌·코드·기록 신뢰와 실행 조건 → 확정된 매도 원인 → 유효한 HOLD 순서다. 저장소 복구로 연구가 다시 유효해져도 신규 진입 권한을 자동 생성하지 않는다.

연구 파일만 손상됐다면 그 파일에 의존하는 연구·승인·전략 판단을 보류한다. 정상 계좌·주문 기록까지 전역 손상으로 간주하지 않는다. 반대로 계좌 저널이나 핵심 코드의 신뢰가 깨졌다면 단순한 연구 보류보다 넓은 실행 차단이 필요하다. 유효한 독립 위험 경로의 존재를 확인하지 않고 “손상 중에도 자동 보호 가능”이라고 주장하지 않는다.

### 5. 보호 상태의 영속화와 재시작

신규 보호 상태 기록은 정상 기록과 같은 검증 가능한 원본 저장 구조를 사용한다. 최소 필드는 보호 인스턴스 ID, 계좌 범위·종목, 코드/프로토콜/정책/검토 해시, 사고 원인, 마지막 정상 입력과 결정 해시, 보유 판단 상태, 위험 최고점과 그 근거, 보호 시작 시각·기한, 마지막 확정 계좌/체결 커서, 주문 시도 ID·상태, 기존 halt 참조다. 비밀 값은 넣지 않는다.

1. OS 단일 실행 잠금을 얻고, 승인된 코드·설정과 저장 head를 검증한다. 신규 진입은 잠긴 상태로 시작한다.
2. 원본 묶음·상태 journal·독립 head의 일치를 확인한다. 오래된 정상 백업을 최신 상태인 것처럼 채택하는 rollback을 거절한다. 복구는 기존 확정 해시와 일치하는 원본 또는 명시적 새 버전 절차로만 한다.
3. 보호 최고점·일일 기준·보호 하한·halt를 복원한다. 값이 없거나 불완전하면 현재 가격으로 새 최고점을 만들어 손실을 허용하지 않는다. 사고 전 전략 시계열의 공백을 가공하지 않는다.
4. 실운영에서는 현재 계좌, 체결·수수료·입출금, 전체 관련 미체결 주문을 조회하여 로컬 기록과 대조한다. 구현 검증에서는 모두 fake transport다. 계좌 밖 주문·동일 종목 다른 전략의 주문이 있으면 임의 취소/매도하지 않고 소유·잔량을 명확히 확인한다.
5. `DISPATCHING`/`UNKNOWN`은 먼저 거래소 주문 식별자/고유 client ID로 대조한다. 응답이 없다고 새 client ID로 재전송하지 않는다. 보낸 적 없는 RESERVED와 보낸 상태를 구분한다. 취소 요청과 실제 취소 완료도 구분한다.
6. 누락·불일치가 남으면 `RECOVERING`/`OWNER_ACTION_REQUIRED` 상태로 유지한다. 재시작 자체로 매도하지 않는다. 독립 계좌 증거가 없는데 이전 high watermark를 안전한 실제 최고점으로 간주하지 않는다.
7. 대조가 끝나면 유효한 범위의 감시와 신규 판단을 재개한다. 보호 매도 자동화의 코드·정책·대상·권한 기한을 다시 확인한다. 신규 진입의 재무장은 별도 유효한 승인 경로만 사용한다.

관측·기록의 원자성이 필요하다. 현재 `Coordinator._work`는 비재진입 Lock(`coordinator.py:476`, `:549`)이므로 모니터 안에서 `submit_exit`를 재진입 호출하지 않는다. 모니터는 매도 의도를 영속화하고 잠금 밖에서 별도 실행 단위를 예약한다. 실행 단위는 자기 계좌·자기 호가로 다시 확인한다. 관측과 주문 저널 lock 순서도 통일하여 계좌 공급자의 중첩 transaction 교착을 만들지 않는다.

### 6. 매도 실행

대상은 **Upbit 원화 현물 유니버스에서 검증된 보유 종목**이다. KIS, OKX, 해외주식, 선물·옵션 또는 레버리지에 이 설계가 적용됐다고 주장하지 않는다. 이종·추가 보유는 보존하며 자동으로 매도하지 않는다.

매도 의도는 `strategy_sell`, 유효한 `trail/risk_band`, 명시적 `owner_exit` 중 하나의 근거를 갖는다. **`hold_deadline`은 주문 원인으로 허용하지 않는다.** 사고 코드가 매도 의도 코드가 될 수 없다. 입력 해시·실제 조건값·정책 버전·판단시각을 묶어 원본 증거로 남긴다. 연구 손상 뒤에는 그 연구를 이용한 전략 매도를 만들지 않는다.

- 주문 직전 현재 계좌·미체결/체결·현재 호가·상품 규칙·시간·기록 가능성·자동 보호 권한을 재확인한다. 기존 halt를 먼저 확인하고 기존 정책대로 자동매도를 차단한다. `RiskResult.protective_action_needed`는 손실·회복 상태를 포함한 넓은 플래그이므로 그 참/거짓만으로 주문을 만들지 않는다.
- 수량은 검증된 보유량에서 모든 관련 미체결 매도 약정량을 차감하고 lot에 맞춘 값 이하로 한다. 취소 요청 중인 잔량도 계속 약정으로 잡는다. 외부 주문과 수량 불일치는 차단한다. 수수료와 최소 수량·최소 명목금액은 최신 규칙대로 확인한다.
- 가격은 그 실행 단위의 **유효한 현재 최우선 매수 호가**와 이미 연구·승인된 슬리피지 범위에서 산정한 지정가를 틱에 맞춰 내린다. 실제 호가 잔량이 충분하다고 가정하지 않는다. 승인 범위를 넘어 할인폭을 늘리거나 시장가로 자동 전환하지 않는다.
- Upbit 유니버스 경로의 IOC를 사용한다. 부분 체결·미체결은 정상 가능한 결과다. IOC 수락 응답만으로 전량 체결이나 잔여 취소 완료를 확정하지 않는다. 가격 급변·얕은 잔량·거래소 중단 때문에 체결되지 않을 수 있다.
- 가격이 내려가 체결이 안 되면 마지막 시도가 종결됐는지 먼저 대조한다. 확인된 미체결 잔량만 새 호가·같은 승인 가격 규칙으로 다시 계획한다. 각 시도는 안정적인 고유 ID를 갖고, 한 시도의 불확실 전송은 같은 시도 ID로 대조한다. 이전 시도가 종결된 뒤에만 새 시도 번호를 만든다.
- 거래소 제한/일시 오류의 재시도는 횟수·최소 간격·현재 규칙의 요청 한도를 존중하는 유한 정책으로 한다. 짧은 무한 반복이나 300초 동안 방치하는 두 극단을 피한다. 구체 재시도 간격은 기존 coordinator 주기와 검증된 API 예산으로 구현 계획에 고정하며 손실 한도를 변경하지 않는다.
- 일부 체결 후 새 계좌 잔량을 기준으로 다음 시도를 만든다. 거래소 체결량·개별 체결 합계·수수료·잔고가 일치할 때만 완료 처리한다. 취소와 체결 경합은 실제 체결을 먼저 반영한다.
- 최소 주문 미만 잔량은 `DUST`로 표시하고 자산·위험 계산에서 삭제하지 않는다. “전량 청산 완료”라고 표시하지 않는다. 활성 매수에서 늦게 들어오는 잔량도 대조 후 관리한다.
- 경계 전후(서울 자정, 기존 회복 판정 시각)에는 새 주문 시도와 계좌 경계 기록을 충돌시키지 않는다. 기존 경계·신선도·하한 조건을 완화하지 않고, 지연 때문에 불가한 주문은 불가 사유와 남은 수량을 보여준다.

이 가격 정책과 감시 주기는 체결 가격·손실 하한을 보장하지 않는다. 저장을 개선하는 것이 급격한 갭·거래소 중단·PC 정지까지 제거하는 것은 아니다. 실제 체결의 슬리피지와 미체결은 그대로 기록한다.

| P3 매도 | 별도 실행 단위, 가격·잔량·IOC·재시도 | S/T/B의 유효 조건에서만 실행; 현재 계좌/호가/규칙 재검사; halt 우선; IOC 0/부분/전부 체결; 취소 경합; 수량 약정; dust; 전송 응답 분실 |

각 단계는 합성 계좌·가짜 주문 전송·임시 홈으로 검증한 후 다음 단계로 이동한다. 예외 코드를 검사하는 것만이 아니라 주문 전송 0회/정확히 1회, 원본 바이트 일치, 주문 ID·수량·체결 증거를 검사한다. 원본 저장 단계가 통과했다고 보호 보유 전체가 완료된 것으로 표시하지 않는다.

보고서에는 `synthetic_boundary_reproduction`, `offline_fault_injection`, `owner_pc_real_incident`를 구분한다. 이번 검토에는 실제 계좌 장애 사례가 없다. 소유자가 `floor_state_check` 미실행이라고 확인했으므로 S1~S12를 임의로 통과 처리하지 않는다. 그 결과가 필요한 PLB 분기는 보류하되 P0/P1 및 테스트 준비는 계속할 수 있다.

### 8. E 최종 결정: 기한 자체 매도 금지, 새 관리 승인 요청

소유자가 확정한 내용: **“기한만으로 매도하지 않고 새 관리 승인 요청.”** 이 항목은 더 이상 승인 질문이 아니다. 기존 A1의 E 자동매도와 그 기본값은 대체한다. 손실 수치·보호 하한·기존 halt 규칙은 그대로다.

- 기한 도달 시 신규 진입 차단을 영속 기록하고, 남은 보유·미체결·승인 만료 상태를 표시하며 새 관리 승인 요청을 만든다. 알림 전송 성공 여부는 이 상태 전이의 성공/실패와 별도로 기록한다.
- 기한 연장, 암묵적 유예 기간, 미응답 자동 승인, 이전 승인으로 새 프로그램/자료를 승인하는 동작은 없다. 새 관리 승인에 대상 코드·자료·정책·계좌 범위·기한을 고정한다.
- **여전히 유효한 독립 관리 권한**이 사전에 부여돼 있고, 현재 필요한 원본·연구·코드·위험 검증이 모두 통과할 때에만 그 범위의 기존 위험 관리 또는 전략 매도를 수행한다. 신규 진입 기한이 끝났다는 사실이 그 자체로 독립 권한을 만들어 주지 않는다. 연구 검토 만료도 임의 연장하지 않는다.
- 주문 권한이 만료됐거나 그러한 독립 권한이 없다면 자동 주문 없이 읽기 전용 감시를 수행한다. 이 감시도 기존 `monitor_until`과 허용 범위를 넘기지 않는다. 감시 기한까지 끝나면 `OWNER_ACTION_REQUIRED`로 인계하고 “자동 보호 종료 / 보유 잔량 존재”를 분명히 표시한다. 종료 뒤에도 작동하는 것처럼 상태를 유지하지 않는다.
- 기한 직전 제출된 매도의 미체결·부분체결은 신규 기한 매도를 만드는 근거가 아니다. 대조와 취소를 수행할 수 있는 기존 별도 권한의 유효 범위에서만 관리한다. 잔량이 있더라도 자동으로 새 시도 번호를 만들어 매도 주문을 재개하지 않는다. 새 관리 승인 또는 유효한 독립 매도 근거가 필요하다.
- 만료를 기점으로 자동 주문을 하지 않더라도 기존 위험 한도가 완화되는 것은 아니다. 손실 위험·미체결 위험·실행 불능을 기록하고 알리며, 하한/최고점/halt를 낮추거나 리셋하지 않는다.

### 9. 숨은 종단 청산 경로와 연구 버전 변경

E 상태만 고치는 것으로는 최신 요구를 만족하지 못한다. 현재 코드에 **창 종료 시 목표 수량을 강제로 0으로 만드는 경로**가 있다. 이 결과를 전략의 자발적 SELL로 포장하면 기한 자동매도를 우회 실행하게 된다.

**운영 정책과 연구 종료 회계를 분리한다.** 연구 표본이 끝난다는 것은 실제 거래소에서 해당 가격으로 매도 체결됐다는 뜻이 아니다. 새 연구는 관측 종료 시 보유 수량·현금·평가 가격과 그 출처/시각을 보존하고 종단 순자산가치를 계산할 수 있으나, 이를 실현 순이익이나 체결된 매도로 표기하지 않는다.

- 새 `protocol/evaluator/driver` 식별자에 종단 정책, 관리 기간·권한, 잔량 평가 규칙을 포함하고 코드 해시와 함께 고정한다. 새 연구 식별자·버전으로 사전등록하고 새 자료/새 결과 검증 및 필요한 새 승인을 받는다. 기존 “창 종료 시 전량 청산” 서명을 새 계속보유 정책에 재사용하지 않는다.
- **실현 순손익**, **미실현 평가손익**, 실제/시뮬레이션으로 발생한 수수료, 미집행 청산을 가정한 별도 비용 시나리오를 구분한다. 잔량이 남으면 `terminal_units`를 실제 값으로 남기며 왕복 거래 완료 수에 가짜 청산을 추가하지 않는다.
- 종단 평가는 사전등록한 가격·통화 환산·신선도/가용성 규칙에 따른다. 유효한 종단 가격이 없으면 임의 0이나 과거 가격으로 정상 성과를 만들지 않고 해당 연구의 평가 불가 결과로 보존한다. 상장폐지처럼 명시적으로 정의한 0평가와 조회 실패를 구분한다.
- 청산 비용을 반영한 보수적 평가를 병기하는 경우 그것은 **가정된 평가 비용**으로 명시한다. 계좌 실현 손익·실제 수수료·체결 기록에 넣지 않는다. 완전 체결 가정은 체결 가능성 증거를 대신하지 않는다.
- 정책 변경으로 표본 말기 노출과 왕복 횟수가 달라지므로 성과 기준·benchmark·다중 시도 회계·선발 근거를 새 버전 전체에서 일관되게 검증한다. 이전 연구 결과는 역사적 원본으로 보존하며 새 버전 통과 증거로 이름만 바꾸지 않는다.
- 연구 관측 종료 이후의 손익을 해당 연구의 관측 성과에 끼워 넣지 않는다. 별도 관측·관리 연구가 이어지면 새로운 창/식별자/승인 범위를 가진다. 승인 요청이 아직 처리되지 않았다는 이유로 연구 데이터를 무한히 덧붙이지 않는다.

#### 단계별 추가 검증

- **P1:** E 직전/동일/직후에서 단독 기한 이벤트는 매도 의도·주문 0건. 유효한 전략 SELL과 우연히 동일한 시각이면 기한과 별개인 입력·정책·승인 근거를 검사한다. 권한이 그 시각에 만료됐으면 새 자동 주문 0건이다.
- **P2:** 기한 직전·상태 기록 직후·승인 요청 전송 직후에 재시작해도 deadline이 갱신되지 않고 요청 중복이 승인 중복으로 이어지지 않는다. 통신 실패·미응답은 계속 승인 대기다. 만료된 매도 시도는 새 주문으로 부활하지 않는다.
- **P3:** 드라이버의 기존 terminal `target=0`과 dust 거절이 새 정책 경로로 새어 들어오지 않는 end-to-end 회귀를 추가한다. 기존 정책 버전은 과거 재생을 정확히 유지한다. 별도 위험 권한 유무, 주문 권한 만료와 monitor_until 경계를 분리해 검사한다.
- **P4:** 새 평가기가 잔량을 보존하고 가짜 체결·실현 수익·수수료를 만들지 않는지 검증한다. 동일 원본에 대한 기존 청산 평가와 새 비청산 평가가 다른 프로토콜/평가기/결과 digest를 가져야 한다. 예전 서명으로 새 결과가 승인되지 않아야 한다.
- **P4:** 실제 계좌 보고의 실현 순손익과 연구의 평가수익이 혼합되지 않는지, 벤치마크에도 동일 종단 정책을 적용하는지, 보유 후 가격 하락 및 유효 가격 누락을 평가 실패/위험으로 정직하게 표시하는지 검사한다.

이 변경은 저장 용량 패치만의 범위가 아니므로 원본 보존(P0) → 보호 상태/기한 상태(P1) → 재시작/승인 대조(P2) → 매도 실행(P3) → 새 평가·선발 계약/운영 통합(P4)의 순서로 검증한다. P0의 독립 개발과 합성 경계 검증은 E 결정 이후에도 바로 이어갈 수 있다. 실거래 활성화와 실제 주문은 여전히 별도 승인·준비 영역이다.

이 문서는 소프트웨어 설계 검토이며 법률·세무·투자 조언이 아니다. 작성자는 면허를 가진 자문가가 아니다.

## C. 확정된 기한 정책과 단계별 진행

사용자 응답: **“기한만으로 매도하지 않고 새 관리 승인 요청.”** 이 결정은 확정됐으며 다시 질문하지 않는다.

- 보유 기한 도달 자체로 SELL 의도나 지정가/시장가 주문을 만들지 않는다. 신규 진입을 중지하고 새 관리 승인 요청을 생성한다.
- 기존에 유효한 독립 관리 권한과 유효 자료가 있을 때만 감시·기존 위험 보호 경로를 계속한다. 권한 만료 시 자동 주문 없이 읽기 전용 감시·알림·소유자 인계 상태다. 읽기 권한/monitor 기간도 끝나면 계속 감시 중이라고 표시하지 않는다.
- 연구 검토 승인과 관리 권한은 별도다. 새 관리 승인도 연구의 재사용/새 진입/세션 활성화를 자동 승인하지 않는다. 재승인 전 임의 유예기간·자동 연장·halt 해제를 만들지 않는다.
- `hold_deadline`, `research_review_expires_at`, `reduce_authority_expires_at`, `monitor_until`을 별도 필드로 둔다. 같은 만료 시각으로 계산됐다는 이유로 다른 권한을 연장하지 않는다.
- 기존 연구의 마지막 슬롯 target=0/강제 종료 청산이 운용상의 기한 매도로 우회 연결되지 않도록 새 정책 버전에서 명시적으로 분리한다. 과거 서명된 연구/기록은 변경하지 않으며 새 정책을 기존 서명으로 승인됐다고 하지 않는다.

실제 코드 통합은 저장(P0) → 판단 상태(P1) → 장애·재시작 복구(P2) → 매도 실행(P3) → 운영 연결(P4) 순서다. 각 단계에서 원본 보존·상태/주문 부작용·기존 하한 회귀를 통과한 뒤 다음으로 진행한다. 저장 계층 자체의 commit crash 검증은 P0에 포함하며 보호 관리자의 복구는 P2에서 다룬다.

이미 확정된 원본 보존·오류만으로 매도하지 않음·하한 유지·시장 범위를 다시 승인받지 않는다. 청크 크기·codec·해시 도메인 등은 근거와 검증을 갖춰 개발자가 정한다. 배포 경로·백업 위치·HTTPS 운영 값은 실제 배포 전에만 필요하다.

사용자가 floor_state_check를 실행하지 않았다고 확인했다. 실제 로그·키를 읽거나 결과를 가정하지 않았다. PLB의 상태 의존 분기 전에 사용자 PC의 S1~S12 고정 코드가 필요하며, 이와 무관한 저장 구현·검증은 진행한다.
