# 전략·고정 실행기 검토 서명

이 절차는 실제 자료를 검토한 소유자가 연구 데이터 출처와 고정 실행기 구현에 대한 서명을 남기는 방법입니다. 코드 승인, 연구 검토, 계좌 연결, 세션 활성화는 각각 별도 요건입니다. 파일 작성이나 `PASS` 문자열만으로 어느 요건도 충족되지 않습니다. 이 개발 작업에서는 실제 키를 사용하거나 서명·활성화·주문을 하지 않았습니다.

## 먼저 준비할 자료

- `request-review`로 생성한 **실제로 계산된 검토 요청**. 사전 등록, 원본 출처, 독립 수집 기간, 시도한 모든 후보·재시도와 비용·위험 기준을 확인해야 합니다. `synthetic`·`retrospective_replay` 자료, 계산 기준 실패, 미완성 프로필은 서명 대상에서 거부합니다. 파일의 prospective 표시는 출처 인증을 대신하지 않습니다.
- 실제 배포의 고정 실행기 명세. 검토된 배포 코드에서 `make_fixed_driver(...)`로 만든 객체에 대해 `dataclasses.asdict(describe_fixed_driver(driver))`를 JSON으로 내보냅니다. 같은 명세를 임의 작성해도 실행 시에는 팩토리가 발급한 실제 객체와 콜백을 다시 검사합니다. 공개된 일반 CLI만으로 완성된 실전 런처가 생기지는 않습니다.
- 본인이 확인한 근거를 적은 별도 감사 문서(`.md`, `.txt`, `.pdf`, `.json`, 최대 1 MiB). 원본 출처, 게시 시각, 전체 후보군, 인과적 의사결정, 실제 프로그램·배포 코드, 자금·수수료·위험 적용을 다룹니다. 키·비밀번호·계좌번호를 적지 않습니다. 서명에는 문서 내용 대신 정확한 바이트의 SHA-256이 들어갑니다. 원문은 별도로 안전하게 보관합니다.
- 최종 코드 및 규칙 승인이 확인되는 실제 소유자 환경. 이 서명은 누락된 소유자 승인이나 다음 서울 날짜부터 효력이 생기는 완화된 한도를 대체하지 않습니다.

## 소유자 실행 순서

1. 최종 변경사항과 `tools/signer/sign.py`를 검토합니다. 새 `review-approve` 명령 때문에 이전의 신뢰한 복사본을 자동 갱신하지 않습니다. 직접 검토하고 저장소 밖의 signer 복사본을 갱신한 다음, 그 SHA-256을 종이에 다시 기록합니다.
2. 시작 메뉴에서 직접 Windows Terminal을 열고, 기존 절차대로 signer 해시와 기록을 비교하고 배포 `.venv`의 `.pth` 파일을 확인합니다. 기존 허용 목록 외의 파일이 있으면 중단합니다. **배포 `.venv`의 Python을 `-I`와 함께 사용**합니다. 서명 암호는 이 터미널에서만 입력합니다.
3. 최종 배포 코드의 `code-approve`를 먼저 수행합니다. 아래 명령은 현재 코드 승인과 현재 공개키를 확인하고, 확인 중 코드·키·감사 문서·입력 파일·소유자 로그가 바뀌면 거부합니다.
4. 필요한 검토를 실제로 완료한 뒤 다음 형식으로 실행합니다. 경로·만료 시각은 본인의 값으로 바꿉니다. 만료 시각은 UTC 마이크로초 형식이고, 서명 시각 이후 최대 24시간이며 연구 요청의 검토 기한 이내여야 합니다.

```powershell
& "<TRADEGEN>\.venv\Scripts\python.exe" -I "<신뢰한 signer>\sign.py" review-approve --repo "<TRADEGEN>" --request "<개인 자료>\review-request.json" --driver-manifest "<개인 자료>\fixed-driver.json" --audit "<개인 자료>\source-review.md" --expires-at "2030-01-01T01:00:00.000000+00:00" --output "<개인 자료>\signed-review.json"
```

위의 2030년 시각은 형식 예시입니다. 실제 연구 기간과 현재 시각에 맞는 값을 입력해야 합니다. 회전한 키를 사용한다면 기존 절차의 `--key "<새 키 파일>"`도 지정합니다. 키 회전 후 현재 PEM을 갱신하는 기존 절차를 그대로 따릅니다.

5. 화면의 전체 바인딩, 만료, 감사 문서 해시, 승인할 체크 항목을 확인합니다. 표시된 무작위 코드를 직접 입력한 뒤 암호를 입력합니다. 복사·붙여넣기는 거부하며 확인은 5분 안에 완료해야 합니다. 기존 파일을 덮어쓰지 않습니다.
6. 생성된 서명 파일은 검토된 런처에 공급합니다. 런처는 실행 때마다 실제 소유자 로더로부터 새로 검증한 컨텍스트와 **현재 PEM 공개키**를 받아 검증해야 합니다. 개발 에이전트에게 키·암호를 보내지 않습니다.

## 실행 시 검증 계약

`execution_launch.review_auth.ReviewVerifiers(document, clock=..., authority_provider=..., approved_history_provider=..., approved_history_verifier=...)`의 `source(binding)`와 `implementation(binding, driver)`를 기존 검증 콜백 자리에 연결합니다. `authority_provider(now)`는 매 호출마다 신뢰한 로더의 `ReviewAuthority(context, public_key_raw, observed_at)`를 반환해야 합니다. `observed_at`은 실제 조회 시각이며 캐시된 컨텍스트에 현재 시각을 붙이면 안 됩니다. 검증기는 30초 초과된 조회, 봉인되지 않았거나 변형된 컨텍스트, 다른 서울 날짜, 중지 상태, 미승인 코드, 다른 현재 키와 서명을 거부합니다. 첫 역사적 키의 지문은 현재 키의 지문을 대신하지 않습니다.

별도 도메인 `tradegen-strategy-review/1`의 Ed25519 서명을 검증하며 기존 소유자 로그 서명 도메인과 호환되지 않습니다. 요청은 원본 프로토콜·계산된 결과·후보 등록부·입력·프로필 계약·위험 조건·전략·프로그램을 함께 묶습니다. 구현 검토는 고정 팩토리 ID, 실제 코드 파일 명세, 배포 기간도 묶고 현재 등록된 객체·콜백 및 명시적으로 선택한 두 이력 의존성의 객체 동일성을 검사합니다. 전체 배포 코드 해시는 현재 소유자 컨텍스트의 코드 승인과 일치해야 합니다.

같은 유효한 바인딩을 다시 검증하는 것은 허용됩니다. 이 문서는 1회용 주문 권한이 아닙니다. 다른 결과·프로그램·프로필·배포 기간·코드·키에 재사용하거나 만료 후 사용하는 것은 거부합니다. 검증 결과를 다른 시각으로 다시 계산하면 결과 해시가 달라질 수 있으므로 원래 결과를 정확히 재현하거나 새 검토가 필요합니다. 소유자 로그에 새 이벤트를 추가하거나 이벤트 스키마를 변경하지 않습니다.

## 아직 별도로 필요한 연결

고정 실행기 객체 확인은 **실시간 이력의 원본 신뢰성**을 증명하지 않습니다. 서명된 연구 원본 검토도 앞으로 도착할 거래소 데이터의 진위를 증명하지 않습니다. `approved_history_provider`와 `approved_history_verifier`는 검토된 배포가 명시적으로 선택하는 신뢰 경계이며, 객체가 같다는 사실은 그 코드나 원본이 안전하다는 암호학적 증명이 아닙니다. 이력 기록, 불변 슬롯/계좌 앵커, 재시작 시 재생은 `execution_launch.live_history.LiveHistory`가, 소유자 컨텍스트 조회는 `execution_control.owner_authority.CurrentOwnerAuthority`가 구현합니다. 그 구현의 배포 검토와 실제 배포 연결, 그리고 최신 계좌·공개 호가·수수료 정보를 공급하는 연결은 아직 별도로 남아 있습니다. 이 서명 파일만으로 실전 준비가 완료되었다고 표시하면 안 됩니다.

실제 세션 ID에 대한 소유자 활성화와 경고 확인, 적용 중 한도, 당일 기준선, 최신 데이터, 주문 게이트는 계속 독립적으로 적용됩니다. 수익 목표나 원금 보장은 서명 대상이 아닙니다. 법률·세무·투자 조언이 아니며 면허를 가진 자문가가 아닙니다.
